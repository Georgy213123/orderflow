# ADR-0004. Статусы заявки — машина состояний на сервере

- Статус: принято
- Дата: 2026-10-23

## Контекст и проблема

У заявки пять статусов: новая, разобрана, конструкция готова, смета готова, отправлена
клиенту. Сейчас статус живёт в переписке. Если статус может поставить кто угодно,
появятся «сметы» без конструкции и отправленные клиенту неполные итоги.

## Факторы решения

- нельзя перепрыгнуть шаг;
- условия перехода проверяются в одном месте;
- понятное сообщение, почему переход не разрешён;
- история переходов для руководителя.

## Рассмотренные варианты

1. Поле статуса, которое клиент API меняет напрямую (`PATCH status`).
2. Таблица разрешённых переходов на сервере, статус меняется как следствие действия
   (сохранили конструкцию — «конструкция готова»), плюс явный запрос перехода только
   для «разобрана» и «отправлена клиенту».
3. Библиотека конечных автоматов с декораторами.

## Решение

Вариант 2. `app/domain/status.py` хранит таблицу `ALLOWED`, `check_transition`
бросает `TransitionError`. Сервис добавляет условия предметной области: для
«разобрана» — все обязательные поля подтверждены, для «отправлена клиенту» — смета
полная. Ответ на нарушение — 409 с `message` и списком `problems`. Каждый переход
пишется в `status_changes`.

Откат назад разрешён один: смета готова → конструкция готова, когда конструктор
меняет параметры. Смета при этом удаляется как устаревшая.

### Последствия

- Хорошо: фронт не решает, что можно; кнопки только отражают ответ сервера.
- Хорошо: таблица переходов маленькая и полностью покрыта тестами.
- Плохо: новые статусы (производство, документы) потребуют расширять таблицу
  и условия. Для демо этого достаточно, для маршрута производства понадобится
  отдельная сущность заказа.
